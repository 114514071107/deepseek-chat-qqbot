## F06：统一发送接口

`qq_delivery.py` 提供 `QQDelivery.send(target, chain, mode='reply') -> DeliveryResult`；插件 `_send` 保留显式 `Target` 要求并返回该结果。

| 字段/状态 | 含义 |
| --- | --- |
| `accepted` | 消息接口返回可取得的消息 id；只表示平台接受，不证明 QQ 客户端收到 |
| `failed` | 明确拒绝，或消息未提交前的准备/上传失败 |
| `unknown` | 发消息超时、连接中断、5xx、HTTP 成功但缺少可验证消息回执；不无条件重发 |
| `skipped` | 空内容、缺凭据、过期、次数耗尽、已关闭的本次凭据等 |
| `stage` | route / credential / prepare / upload / message / synthesis |
| `category` | permission / rate_limit / expired / exhausted / duplicate / route / media / network 等 |
| `message_id/ref_idx/seq` | 可取得的平台标识、引用索引及实际使用序号 |
| `attempt_id/persistence/fallback_from` | 投递条目标识、各层持久化状态及一次回退的前置结果 |

错误只保存分类和错误码，不保存 SDK 异常原文、响应 message、发送正文、令牌或目标地址。接口存在、没有异常、HTTP 2xx、上传成功都不单独构成 accepted。

- `Scope/Target` 增加 `event_id/received_at` 默认字段，不改变 v2 会话/个人/群键。只在可信事件首次绑定时取时间，不被后续 hook 刷新；历史中老 Scope 缺字段仍能读取，缺凭据不能猜测成新被动回复。
- 同一实例/机器人/场景/目标/有效触发凭据共用锁、序号和次数。优先 msg_id，否则 event_id；同 msg_id 的重复投递即使 event_id 不同也共用账本。序号从 1 递增，已提交的失败/未知序号不回收。
- 气泡、抢答、工具忙碌反馈、表情、语音、文件与短延时延续使用原触发 Target。过期不丢掉 msg_id 改走主动；没有平台匹配不换机器人或私聊。
- 真正定时主动、上线问候、既有定时提醒、受保护控制台代发显式指定 `mode='proactive'`，不附旧 msg_id/event_id。原开关、私聊主动授权、额度和任务身份继续生效；未制定无权限后的长期停用/通知/恢复政策。闹钟专项未实施，原闹钟直发路径仍属暂缓项，不能把本单称为闹钟修复。
- 使用 AstrBot 的媒体解析/本地语音转换和 botpy 已认证会话；消息与上传实际 POST 各一次，绕过会吞超时、重试、改为主动或 Markdown 降级的旧发送 helper。无 SDK 消息重试、无换路径重发。消息失败会终止当前回复链；明确媒体故障可在剩余凭据额度内回退一次文字。
- 发送前、上传后、鉴权 await 后检查请求及框架权限。取消提交中的消息保留 unknown；已交给平台的请求无法撤回。凭据账本保留在框架 context，辅助模块重载不重置；进程重启不恢复在途任务，也不自动重放投递账本。

## F07：请求结束和历史

`ReplyPlan` 绑定事件、Target、请求 token、气泡、媒体和语音动作。`capture` 只整理内容与显示预览，不再预写 assistant 历史。`_complete_reply(event)` 至多消费一次；`_finish_reply(event)` 清理对应状态，核对请求和实际主事件两个身份。

- 气泡按原间隔发送，每条 accepted 后单独入历史；首条失败不续发，部分成功只保存已接受部分。新消息、删除、禁用和终止仍通过前两单 Runtime 撤销。
- 纯表情本轮直接发送；待发表情移入具体计划，不留给下一轮。所选表情仅在 accepted 后更新 last_sticker。
- 语音保留原合成 150 字上限；成功记录实际语音文本和具体 voice 路径。无服务、合成或明确媒体失败时回退完整原文字一次；权限、路由、频控、过期、耗尽、撤销及消息结果未知不盲目回退。回退本身继续消耗同一触发凭据并受生命周期约束。
- 文本与媒体混合链明确媒体失败时，同样只有一次纯文字回退；纯媒体链也纳入当前计划。
- 每条 accepted 历史拥有条目 id、request_id 和 delivery 信息，媒体随该条一次写入滚动、群历史及归档；删除了“挂到 uid 最后一条 assistant”的路径。同一人在群和私聊同时发起的语音，各自关联自己的条目。
- 平台接受与 rolling/group/archive/framework/receipt 保存结果分开；三份文件并非跨文件事务。某层保存失败会如实留下 failed，不能据此重发 QQ 消息。内存里的 accepted 内容可供当前进程使用，磁盘失败意味着重启后可能缺失，需按层核对恢复。

`reply_integration.py` 在构造时幂等安装 AstrBot 4.29.1 的内存适配，未编辑 site-packages：

1. RespondStage 在空链检查前消费计划。
2. 框架历史保存入口也消费尚未发送的计划，覆盖 completion_text 清空后 runner 根本不 yield RespondStage 的情况。
3. Scheduler 正常返回时作最后一次幂等消费，finally 清理；异常/取消不会在 finally 启动回退或新发送。攒批第二条事件虽然共享 token，也没有主事件的结束权；迟到旧 hook 校验失败前不能重新登记清理权。
4. QQ 事件直接发送也使用统一结果并保存已接受的可见内容，包含框架工具前文字/工具提示；不依赖 after_message_sent 回调证明成功。
5. 框架 `_save_to_history` 不再保存完整生成轨迹和工具轨迹，而投影当前插件已接受历史；请求仍使用 F01 的插件来源历史作为唯一输入。配置不变，QQ 的流式/live 输出统一进入有限气泡/语音动作路径，避免未核验流式片段提前外泄。

**兼容影响：** 新写入的 assistant 有可核验投递语义；不重写旧 assistant 数据，也不推定旧条目曾送达。框架保存投影排除缺少 accepted 凭据的旧 assistant，插件原有 v2 旧历史仍按前两单规则可读。正常最终保存是当时的快照；后续延续消息以插件/归档为权威，框架不会被当成另一份更完整模型历史。完整生成内容不再作为“已经说过”的文本保存；工具轨迹可能仍存在框架遥测中，不作为对话上下文。更新框架前必须重新验证这些内部集成点。

另增 `delivery_receipts_v2.json`，按会话保存无生成正文的发送结果元数据。提交消息前写 unknown/in_flight，同一 attempt_id 在得到明确结果后更新；任务被撤销或进程中断时，不能把缺少最终更新解释为明确没发。投递账本写入失败也独立报告，不影响平台结果、不触发重发。它属于 F08 **归档层**：按来源删除，其他来源保留；只删滚动历史会保留该账本，未加自动到期清理。
