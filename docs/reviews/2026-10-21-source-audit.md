## R01：重定向绕过网页抓取的内网检查

**位置：** [main.py:2497](../../plugin/astrbot_plugin_dsh_soul/main.py#L2497)、[main.py:2506](../../plugin/astrbot_plugin_dsh_soul/main.py#L2506)。

`fetch_url` 是普通用户也可触发的工具。`_is_internal_url()` 只校验初始 URL 的解析地址；后续直接使用默认 `urllib.request.urlopen()`，而标准库默认处理 HTTP 重定向，新的目的地址不再经过插件检查。

**触发与影响：** 初始页面通过公网地址检查，随后重定向至本机或内网服务。返回正文会进入工具结果及模型上下文，绕过“不能访问内网”的约束。结合 R02，本机控制台默认的 `/api/history` 就会返回主人记录，不要求攻击者提前知道主人 ID。

**验证边界：** 本项为静态确认，未对真实内网或真实用户记录执行请求。证据是首跳检查的位置、默认 opener 的自动重定向行为，以及工具对普通用户开放的过滤配置。

**修复方向：** 对每一跳重新检查目标及连接地址，限制协议和重定向次数；控制台仍应有独立鉴权，不能仅依赖 URL 检查保护它。

## R02：控制台管理接口没有独立鉴权

**位置：** [server.js:488](../../console/server.js#L488)–494；请求体解析 66–70；用户记录接口 127–144、156–180。

路由直接执行匹配的 GET/POST handler，没有访问令牌、登录态或权限判断。监听 `127.0.0.1` 只限制网络来源，不能区分被允许和不被允许的本机调用者。GET 接口可读取用户列表、聊天记录、长期记忆等；POST 接口可改开关、启停机器人、管理员代发和广播。

`readBody()` 也不要求 JSON Content-Type，路由不校验 Origin。隔离 Node VM 中，带跨站 Origin、`text/plain` 内容类型的 JSON POST 仍返回 200 / `ok:true` 并修改了模拟总开关。

**利用前提：** 调用者能访问这个 HTTP 服务；网页场景还取决于浏览器是否允许访问本地网络。不能据此声称所有现代浏览器都会允许任意网页无提示利用。R01 这样的服务端请求入口不依赖浏览器 CORS。

**修复方向：** 所有敏感 API 统一鉴权；写请求校验 Origin、内容类型与防跨站令牌，检查 Host，继续保持默认本机监听。

## R03：禁用或重载后后台任务仍运行

**位置：** [main.py:3358](../../plugin/astrbot_plugin_dsh_soul/main.py#L3358)–3364；旧状态回写 2974–2982。

`on_loaded()` 通过 `asyncio.create_task()` 创建永久循环，但没有保存句柄，类中也没有清理这些任务的 `terminate()`。AstrBot 4.29.1 的插件管理器在禁用/重载时调用插件定义的终止方法、解绑事件和工具，并不替插件取消任意后台任务。

**触发与影响：** 插件启动过后台循环后，在面板禁用或重载插件，旧实例仍持有自身状态并执行主动消息、闹钟等逻辑。重载后的新实例记录了新历史，旧实例再执行 `_record_assistant_turn()` 时，可把旧的整份 `self.h` 写回，覆盖滚动历史和近期上下文。归档 JSONL 可能尚在，因此这里不是认定全部历史永久丢失。

**修复方向：** 显式管理全部任务，在终止时取消并等待退出；延时发送和外包任务也纳入生命周期管理。

## R04：管理页面修改状态后，旧内存与归档仍生效

**位置：** [server.js:349](../../console/server.js#L349)–381；[main.py:1167](../../plugin/astrbot_plugin_dsh_soul/main.py#L1167)–1184、1233–1234、2971–2972。

控制台的清空历史、删除念头、解除黑名单、解除休眠只修改磁盘文件；核心插件把这些数据缓存于 `self.h/self.th/self.blocked/self.sil`，没有接收变更或重载。

**隔离复现：** 四类管理操作返回成功，文件内容已改变，但插件内存仍是旧状态。随后另一用户产生消息或念头，整表保存会恢复刚删除的用户历史或念头。休眠和黑名单操作也不会立即反映到对应判断中。

此外，清历史接口只处理 `history_all.json`，不清 `history_archive.jsonl`；`recall` 和历史查询仍能从归档读回旧内容。即使重启清掉旧内存，也不能把这个接口当作完整的聊天记录删除操作。

**修复方向：** 让运行插件统一管理状态变更，并明确区分“清上下文”和“删除历史”；完整删除覆盖滚动记录、归档及其他声明应被清除的存储。

## R05：异步发闹钟时覆盖并发修改

**位置：** [main.py:3463](../../plugin/astrbot_plugin_dsh_soul/main.py#L3463)、3477–3484。

处理循环先读取整份 `alarms`，逐条保存，再 `await _fire_alarm()`。第一个闹钟发送期间，其他事件可以新增或取消闹钟；处理第二个到期闹钟时却把旧列表整体写回。

**离线复现：** 初始闹钟 `[1,2]`；发送第一个时新增并保存 `3`；处理第二个后磁盘只剩 `[1,2]`。取消操作也可能被反向恢复，造成已取消的提醒继续发送。

**修复方向：** 在锁或事务中更新具体闹钟，避免跨越网络 await 后保存旧快照；发送与状态变更分离。

## R06：语音后下一轮被当作“旧轮打断”吞掉

**位置：** [main.py:1519](../../plugin/astrbot_plugin_dsh_soul/main.py#L1519)–1522；1657、2840–2841、1450–1456。

语音分支清空文字结果链，另起任务发送语音。AstrBot 4.29.1 在 `respond/stage.py:203–208` 遇到空链直接返回，不触发 `after_message_sent`，因此 `post_send()` 中清理 `run_active` 的逻辑没有执行。直接 `context.send_message()` 也不会代替事件管线触发这个回调。

**离线复现：** 第一轮语音路径结束后，生成中标志仍存在。90 秒内下一条消息被 gate 设置 `interrupt=True`，新生成的正常答案进入 capture 后被全部清空。这与语音服务是否成功是两个问题。

**修复方向：** 将生成状态清理放在可靠的请求终止路径，不依赖“文字已经发送”这个事件；用请求代号关联打断标志。

## R07：语音失败没有文字回退

**位置：** [main.py:1521](../../plugin/astrbot_plugin_dsh_soul/main.py#L1521)–1522；1747–1749、1762–1763；历史写入 1510–1515。

调用 TTS 前已经清除文字并记录 assistant 历史。TTS 失败只记日志，不发送原来的文字，也不撤销“已经回复”的历史。

**离线复现：** 模拟语音服务连接失败，结果是 `text_cleared=True`、实际发送消息数 `0`、assistant 历史仍被写入。未部署 TTS 时，只要模型输出语音动作就可能触发。

**修复方向：** 语音生成/发送失败后回退文字，历史按真正成功发送的内容更新。

## R08：攒批缓冲丢失补发图片

**位置：** [main.py:2843](../../plugin/astrbot_plugin_dsh_soul/main.py#L2843)–2850；合并点 1285–1294。

先发问题，随后在攒批窗口内补发纯图片时，第二个事件被 `stop_event()` 终止。缓冲只保存非空文本，注入主请求时也只拼接文字，没有迁移图片到 `req.image_urls`。

**离线复现：** 第二条图片事件被终止，主请求的图片列表仍为空；历史虽有图片占位或路径，但那不是本次识图请求的图像输入。

**修复方向：** 缓冲完整消息及媒体组件，合并图片输入；或保留图片事件的独立处理。

## R09：只有表情动作时不发图

**位置：** [main.py:1480](../../plugin/astrbot_plugin_dsh_soul/main.py#L1480)–1489；1659–1662。

纯表情回复把图片放进 `pending_sticker`，同时清空结果链；发送图片却完全依赖 `post_send()`。空链导致框架跳过回调，当轮图片不发送。

**离线复现：** 返回结果链长度 `0`，待发表情数量 `1`。后续一次有文字的回复才可能把遗留图片补发，造成无响应或表情错轮。

**修复方向：** 将表情纳入可发送结果链，或显式发送，不依赖被空链跳过的回调。

## R10：三个闹钟限流与严格分钟匹配不兼容

**位置：** [main.py:3467](../../plugin/astrbot_plugin_dsh_soul/main.py#L3467)–3469；692–697。

注释说超过三个的闹钟顺延下一分钟，但 daily/weekly 只有在当前 `HH:MM` 严格等于目标时间时才到期。

**离线复现：** 四个循环闹钟同为 `12:00`。`12:00:30` 检查只触发前三个；45 秒后的 `12:01:15`，第四个已经不满足到期判断，漏掉当日提醒。这三个名额还是所有用户共用。

**修复方向：** 对到期事项排队，记录实际计划触发时间，允许限流后的延迟处理。

## R11：控制台自重启会争用旧端口

**位置：** [server.js:264](../../console/server.js#L264)–266、502。

先启动同端口的新进程，旧进程再等 500ms 才退出。新进程如果在旧端口释放前监听，会因未处理的 `EADDRINUSE` 退出；旧进程随后也退出。

**隔离复现：** 临时数据目录、随机端口中，重启接口返回 `ok:true`，新进程记录 `EADDRINUSE`；1.8 秒后连接被拒绝。未操作真实控制台。

**修复方向：** 先释放端口再交接，或让外部监督进程执行重启，并根据真实健康状态返回结果。

## R12：普通用户可修改和移走全局图库文件

**位置：** [main.py:2567](../../plugin/astrbot_plugin_dsh_soul/main.py#L2567)–2573；2605–2622；工具过滤 1417–1426。

`retag_sticker/delete_sticker` 没有主人或图片归属检查，也没有被普通用户工具过滤器剔除。图库是共享的，普通用户可以通过模型调用管理工具，操作其他人收集的图片或共用表情包。

**临时图库复现：** 以普通用户事件调用删除工具，测试图片被移入 `_trash`，共享数据库中的图片行被删除；身份从未被检查。操作可恢复，但能破坏其他用户和机器人的正常用图。

**修复方向：** 将全局图库管理限制给主人，或实现明确的图片归属与管理权限；普通用户可以继续检索授权范围内的图片。

## R13：TTS 输出临时文件没有生命周期清理

**位置：** [tts_server.py:160](../../tts/tts_server.py#L160)–165、168–199。

WAV 分支直接返回临时 WAV；MP3 分支只删除中间 WAV，留下输出 MP3。两者都没有响应结束后的删除回调。插件侧只清理自己的 `media/voice`，清不到独立 TTS 服务的系统临时目录。

**隔离复现：** 替身推理生成三次 WAV，使用真实 Starlette FileResponse 完整发送三个响应，临时目录仍留有三个输出音频，且 response.background 均为空。测试结束后清理临时目录。

**触发条件：** 启用独立 TTS 服务且持续使用语音。长期运行时临时文件持续积累，最终可能影响磁盘可用空间。

**修复方向：** 响应发送完毕后删除输出文件，并为异常、断连和历史遗留文件提供清理策略。

## 检查结果与边界

- 已有余额插件的两个单元测试通过；Python 编译检查与控制台 JavaScript 语法检查通过。这些检查不能覆盖以上运行时交错和框架回调问题。
- 本轮没有在余额插件中确认同等级问题；其已有测试仅覆盖权限辅助函数与余额文本格式，不能代表真实 API 和 QQ 指令的端到端验证。
- R01、R03 根据完整调用路径和所安装框架源码确认，其余项目取得隔离复现结果；未对生产环境执行入侵验证。
- 建议先处理 R01–R03，再统一状态写入与消息结束路径（R04–R09），最后处理限流、控制台重启和资源清理。
- 本报告在本地审查分支记录，未主动公开发布漏洞清单；本轮不修改机器人源码。
