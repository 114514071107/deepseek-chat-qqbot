## A：根因、实现及数量规则

原根因是每次成功 `send_sticker()` 都无条件追加到 pending，模型跨轮再次选择仍能继续累加；先前修复只协调工具与动作的替代关系，没有明确张数上限。本轮不是通过修改提示词、按图片文件去重或强制单张解决。

- `sticker_count_request()` 只读当前事件正文与 inject 保留的同请求入站攒批文字，用已有字面边界遮蔽代码围栏、缩进、引用块、引号与行内代码。不读旧历史、摘要、模型查询词或任意工具参数。长消息完整原文仍参与识别，不能被留存的 2000 字符前缀替换。
- 支持 **0—99 的阿拉伯数字及常用中文数词（含两、十、十二、二十三）+“张”**，对象为“表情/表情包/贴图/图片”；支持“发两张表情”“两张相同的开心表情”“表情包发3张”，以及“共/一共/总共/总计/合计 N 张”。明确总计优先，最后一个总计约定生效；明确请求总数优先于“一张开心表情、一张无语表情”等逐张描述。
- 范围/备选表达（两张或三张、2—3 张）、互相冲突且没有明确总计的数字、不支持的单位或没有数字时，不猜测总数，保持原选择行为并继续受已有工具/资源预算限制。不是任意自然语言数量解析器；不会把分项数字擅自相加。0 表示不入队/不发送图片。
- 请求事件缓存 `{identity, limit, selected, attempted, closed}`，identity 含原 scope 和 request_id。工具队列另核对请求所有者，新请求不会继承旧队列或额度；数量不在每次工具轮次重新计算。`_queue_sticker()` 的检查、选图和占位之间没有 await，并发协程无法抢占同一份剩余额度；达到额度时不再选图，也不会触发上传或发送。
- ReplyPlan 记录并裁剪明确上限；中间 capture 替换尚未开始的同请求计划时，保留之前已选但未发的图片，pending 被消费不等于送达。完成器开始时及每次实际媒体发送前再次按同请求约束检查，尝试在 await 上传前计数。失败/unknown 不释放额度，不盲目补发以凑张数；原单次安全文字回退保留，accepted 才写入已发送历史。上限不等于自动补图承诺：素材不足、模型只选一张、平台失败等不复制或重试凑数。
- 原工具/动作协调保留：已有工具选择时动作行不追加，即使中间 capture 已取走 pending，也根据请求内已选状态判断；无工具选择时动作行可选一张补位，并走同一额度。相同图片两张仍占两个名额、发送两次；不按路径去重。原纯表情等待反馈约束、普通下一轮反馈与代码保护继续受全集覆盖。
- 取消/关闭/删除走既有请求清理并关闭预算，pending 清空；旧请求结束只用该事件已经固定的 Scope，不重新登记旧消息覆盖新请求来源。新预算/ReplyPlan 字段是内存状态，不迁移历史或配置。

失败证据：原探针 2 通过/1 失败；新增初始专项也复现超额。自查额外先取得“下一请求仍夹旧 pending”“总数与逐张描述冲突”“长消息末尾数量被留存前缀盖掉”“中间 capture 丢掉已选图片/后续协议又补选”的失败，再补修。旧完成器来源回写通过临时内存恢复旧 helper 的重绑定行为得到 `old-message != new-message`，最终持久化测试断言新来源不被覆盖。收尾也验证范围连接号不被当成确定数、已结束工具准确返回结束状态。中间版本的 214/214、216/216 保留为当时结果，追加边界后重新跑最终全集，不拿中间数字代替最终结果。

## B：可信关联、读取与管理边界

查阅于 2026-10-25 的腾讯官方[消息事件定义](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/event.md)分别列出单聊 author.user_openid 与群 author.member_openid，后者说明为“用户在本群”的标识。现有 Scope 只保存 platform/instance/bot/sender/group/private 等字段，没有可信跨场景统一身份映射。**未取得这些标识可跨群/私聊等同的保证，因此本实现保守地不自动跨这些身份域合并**；示例字符串相同也不当成保证。没有读取生产身份去猜映射，没有新增 QQ 查询朋友私聊能力。

- 自动归并仅针对完全一致的 platform、instance、bot、场景身份域、sender；群身份域还包含具体 group。昵称、头像、时间和哈希前缀均不参与身份判断。改备注不会拆人，同名不同人保持独立。
- 确认同一人后，管理者可通过受保护工作台人工关联多个来源。映射只写独立 `dsh_data/console_people_v1.json`，不修改 scopes、历史、身份认证、主人权限、积分/记忆或模型上下文。解除可以只拆出一个来源；来源不明旧档保留原入口，禁止猜测关联。映射不随单层聊天删除暗中联动移除，解除关联由维护者显式操作。
- 关联/解除需当前 revision 和 confirm=true，同进程中同步校验并原子落盘；过期列表、重复来源/非法入口被拒绝。每个人工组最多 20 个来源，映射文件最多 1MiB、2000 组；原始元数据/历史 JSON 各自最多 32MiB，来源总数最多 10000，超限明确报错，不偷偷读取全部归档或改数据。
- `/api/people` 分页最多 100 个入口，不返回聊天正文；入口数量与来源会话数量分别展示，不把待确认入口数宣称为真实自然人总数。`/api/people/history` 每来源只取最近 150 条滚动记录，响应每页最多 200 条并提供 offset/next_offset；页面默认 150 条。没有一次性把所有人的聊天正文发给浏览器。
- 已知来源的 user 行必须匹配完整 Scope 身份；assistant 必须同源且 accepted。群助手回复还须 request_id 对应本来源近期 user，关联无法证明时排除并显示数量；私聊同源 accepted 主动回复可保留。群聚合逐条带群、发言者、消息标识及原 scope。群名称缺资料时显示留存的群标识，不冒充数字 QQ 群号。
- 保留旧 `/api/history`、`/api/switches`、媒体和管理接口兼容性。新接口及新前端资源同样先走认证、Host/Origin/写请求保护。聚合 person ID 在开关、积分、删除、直接发送及广播目标入口明确拒绝；即使运行态在线也不下发到管理队列。
- 查看记录不会自动选择操作或发送目标。需要维护开关/积分/删除时，在“管理具体来源”中明确选原 scope，显示完整来源；积分仍按原共享账本只操作一次，不对聚合成员相加/循环赠送。未选来源不渲染可执行控件。删除仍选具体层，通知页发送仍须另选已有目标。
- 用户/场景/群/分页切换通过 AbortController 和请求版本防旧响应回填，切换立即清空旧消息；原 scope 管理历史与删除预览亦检查来源和渲染版本。刷新保留已确认选择；跨来源切换重置操作来源。普通失败、空列表/无此场景、加载中、旧档与重试均有明确反馈。

实现文件：`console/user-workbench.js` 管列表/投影/映射，`console/public/user-workbench.js` 管用户页交互，server.js 接入受保护路由；原 index.html 保留样式与管理组件，只接入新页、可见选中/键盘状态及窄屏布局。视觉沿用原 `#f2f5f9` 背景、`#fff` 面板、`#253047` 正文、`#7a869c` 次文与 `#2f7df6` 操作蓝、原微软雅黑/system-ui；没有重做其余工作台。

## 后台使用方法

1. 打开受保护控制台的“用户”。初次无法可靠确认的群/私聊入口分开显示，旧档标“来源未定”；可翻页查看入口。
2. 选择入口，通过“私聊 / 群聊”按钮查看；群模式可选具体群或全部群，每条消息带群来源。没有对应场景时会说明。记录只含近期滚动范围，支持前后翻页，不代表全归档。
3. 确认不同入口属于同一人：展开“来源与人工关联”，核对 platform、instance、bot、sender、群/私聊及原 scope；选择另一入口（超过一页时可按备注或来源标识查找），点“关联展示”并确认。确认后一个用户入口下包含多个来源。要拆开时选择具体来源，点“解除此来源关联”并确认。昵称相同不能替代身份核对。
4. 需要管理时展开“管理具体来源”，明确选一个原始来源，再使用原积分/开关/删除组件；切换用户/场景/群后需重新选来源。删除仍勾选数据层。查看或关联用户都不会自动选定发信目标；发送请去“通知”另外选择目标。
